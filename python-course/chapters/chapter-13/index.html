🔭 چشم‌انداز فصل: اهداف و جایگاه

تا اینجا با خطاهای مختلفی روبه‌رو شده‌اید: ValueError، TypeError، KeyError، IndexError. هر وقت یکی از این‌ها رخ می‌داد، برنامه کاملاً متوقف می‌شد. اما در دنیای واقعی، این قابل قبول نیست. اگر یک وب‌سایت با یک ورودی بد کاربر از کار بیفتد، فاجعه است.

در این فصل یاد می‌گیرید که چطور این خطاها را مدیریت کنید — یعنی به‌جای کرش کردن، برنامه به کار خود ادامه دهد و پیام مناسبی به کاربر نشان دهد. این یکی از مهم‌ترین تفاوت‌های بین یک برنامه‌ی مبتدی و یک برنامه‌ی حرفه‌ای است.

در پایان این فصل، شما می‌توانید:

  • با try/except خطاها را بگیرید و مدیریت کنید.
  • حالت‌های مختلف خطا را جداگانه مدیریت کنید (چند except).
  • با finally مطمئن شوید کد پاک‌سازی همیشه اجرا می‌شود.
  • با raise خطای خودتان بسازید و پرتاب کنید.
  • استثناهای سفارشی (خودتان) طراحی کنید.
  • با logging رویدادهای برنامه را ثبت کنید (به‌جای print).
  • کِی از try/except استفاده کنید و کِی نه.
📌 نکته مهم هدف این فصل، پنهان کردن خطاها نیست. هدف این است که خطاها را هوشمندانه مدیریت کنید — یعنی بفهمید کجا خطا ممکن است رخ دهد، چه نوعی از خطا، و چطور به کاربر یا برنامه پاسخ مناسب بدهید.

🤔 سوالات محرک ذهنی

قبل از خواندن آموزش، چند لحظه به این سوال‌ها فکر کنید:

🤔 چرا خطاها را «پنهان» نکنیم؟ خوب نیست که برنامه کارش را ادامه دهد؟

این یک سؤال خیلی مهم است. بله، ادامه دادن برنامه خوب است، اما نه به قیمت پنهان کردن واقعیت. اگر برنامه‌ای دارید که باید پول از حساب کاربر کم کند و به دلیل خطایی این کار نشده، ادامه دادن برنامه بدون این‌که کسی بفهمد، فاجعه است! پس قاعده‌ی طلایی: خطاها را ببینید، مدیریتشان کنید، و در جایی که لازم است ثبت‌شان کنید. اما هرگز آن‌ها را کاملاً نادیده نگیرید.

🤔 چرا از logging استفاده کنیم و نه print؟

سه دلیل مهم: (۱) سطح‌بندی — می‌توانید مشخص کنید پیام «اطلاعات» است یا «خطا» یا «هشدار». (۲) ذخیره در فایل — با یک تنظیم ساده، همه‌ی پیام‌ها در فایل ذخیره می‌شوند تا بعداً بررسی کنید. (۳) قابل خاموش کردن — در حالت توسعه، همه‌ی لاگ‌ها را می‌بینید؛ در حالت عملیاتی، فقط خطاها. با print نمی‌توانید این‌ها را کنترل کنید.

🤔 تفاوت except Exception و except ValueError چیست؟

except Exception هر خطایی را می‌گیرد — حتی آن‌هایی که فکرش را نمی‌کنید. except ValueError فقط خطای ValueError را می‌گیرد. شاید فکر کنید اولی بهتر است چون همه‌چیز را می‌گیرد، اما نه! اگر فقط ValueError را انتظار دارید، با except Exception ممکن است یک باگ واقعی در کدتان را پنهان کنید. همیشه دقیق‌ترین except را انتخاب کنید.

📖 آموزش گام‌به‌گام: استثنا و خطایابی

۱) خطا در پایتون — دو نوع

در پایتون دو نوع خطا داریم:

  • خطای نحوی (SyntaxError): وقتی کد از نظر گرامری اشتباه باشد. قبل از اجرا اتفاق می‌افتد.
  • استثنا (Exception): وقتی کد از نظر گرامری درست است، اما هنگام اجرا مشکلی پیش می‌آید. مثل تقسیم بر صفر.

SyntaxError را با ویرایش کد رفع می‌کنید. اما استثناها را می‌توان با try/except مدیریت کرد.

نمونه‌ای از استثنا:

unhandled.pyPython
number = int("سلام")   # ValueError!

# خروجی:
# Traceback (most recent call last):
#   File "unhandled.py", line 1, in <module>
#     number = int("سلام")
# ValueError: invalid literal for int() with base 10: 'سلام'

برنامه با یک پیام طولانی و ترسناک متوقف می‌شود. حالا بیایید همین را با try/except مدیریت کنیم.

۲) try/except — گرفتن خطا

ساختار ساده:

ساختار try/exceptPython

    ...

    ...

مثال:

try:

۳) چند except — هر خطا، پاسخ خودش

ممکن است کدی چند نوع خطای مختلف داشته باشد. می‌توانید برای هر کدام except جداگانه بنویسید:

multiple_except.pyPython
try:
    a = int(input("عدد اول: "))
    b = int(input("عدد دوم: "))
    result = a / b
    print("نتیجه:", result)
except ValueError:
    print("❌ لطفاً عدد معتبر وارد کن.")
except ZeroDivisionError:
    print("❌ نمی‌توان بر صفر تقسیم کرد.")
except Exception as e:
    print(f"❌ خطای غیرمنتظره: {e}")

نکته: except Exception در انتها آمده — به‌عنوان «شبکه‌ی امنیتی» برای خطاهای غیرمنتظره. همیشه exceptهای خاص را قبل از exceptهای عمومی بنویسید.

ترکیب چند خطا در یک except

اگر برای چند خطا یک پاسخ دارید:

combined_except.pyPython
try:
    # کد مشکوک
    ...
except (ValueError, TypeError) as e:
    print(f"خطای نوع داده: {e}")

دقت کنید که باید داخل پرانتز باشند.

۵) else و finally — کنترل کامل

ساختار کامل try/except شامل دو بخش اضافی هم می‌شود:

ساختار کاملPython
try:
    # کد مشکوک
    ...
except نوع_خطا:
    # اگر خطا رخ داد
    ...
else:
    # اگر خطا رخ نداد (اجرا فقط وقتی try موفق باشد)
    ...
finally:
    # هر اتفاقی افتاد، این همیشه اجرا می‌شود
    ...

else — وقتی خطا رخ نداده

else_demo.pyPython
try:
    number = int(input("عدد: "))
except ValueError:
    print("❌ ورودی نامعتبر است.")
else:
    print(f"✅ عدد صحیح وارد شد: {number}")
    print(f"دو برابرش: {number * 2}")

فایده‌ی else چیست؟ اینکه مشخص کنید کدام کد فقط در حالت موفقیت اجرا می‌شود. اگر آن کد را داخل try می‌گذاشتید، خطاهای آن هم گرفته می‌شدند — که ممکن است چیزی نباشد که می‌خواستید.

finally — همیشه اجرا می‌شود

کد داخل finally در هر شرایطی اجرا می‌شود — چه خطا رخ بدهد، چه ندهد، حتی اگر با return از تابع بیرون بیایید:

finally_demo.pyPython
def divide(a, b):
    try:
        result = a / b
        print(f"محاسبه: {a} / {b} = {result}")
        return result
    except ZeroDivisionError:
        print("❌ تقسیم بر صفر مجاز نیست.")
        return None
    finally:
        print("--- پایان عملیات تقسیم ---")


divide(10, 2)
print()
divide(10, 0)

کاربرد اصلی finally: پاک‌سازی. مثلاً بستن فایل، بستن اتصال شبکه، آزاد کردن منابع. با finally مطمئن می‌شوید که این کار در هر حالتی انجام می‌شود.

۶) raise — پرتاب خطا از سمت خودتان

گاهی خودتان تشخیص می‌دهید که چیزی اشتباه است و می‌خواهید خطا بسازید. با raise این کار را می‌کنید:

raise_demo.pyPython
def set_age(age):
    """سن را تعیین می‌کند، ولی باید بین 0 و 150 باشد."""
    if age < 0:
        raise ValueError("سن نمی‌تواند منفی باشد.")
    if age > 150:
        raise ValueError("سن نمی‌تواند بیشتر از 150 باشد.")
    return age


# استفاده
try:
    user_age = set_age(-5)
except ValueError as e:
    print(f"❌ خطا: {e}")

چرا خطای خودمان پرتاب کنیم؟

سه دلیل اصلی:

  • صریح بودن: به‌جای اینکه تابع با یک خطای مبهم متوقف شود، پیام دقیق می‌دهد.
  • اعتبارسنجی: می‌توانید ورودی‌های نامعتبر را رد کنید.
  • قرارداد: کاربر تابع می‌داند چه انتظاری داشته باشد و چه خطاهایی احتمال دارد.

دوباره پرتاب کردن خطا — raise بدون آرگومان

گاهی می‌خواهید خطا را بگیرید، کارهای لازم را انجام دهید، و بعد دوباره پرتابش کنید:

re_raise.pyPython
def process_data(data):
    try:
        return int(data)
    except ValueError:
        # ثبت خطا برای عیب‌یابی
        print(f"❌ ورودی نامعتبر: {data}")
        # دوباره پرتاب کن — تا فراخوان هم بفهمد
        raise

۷) استثناهای سفارشی — خطاهای خودتان

برای پروژه‌های بزرگ، بهتر است خطاهای مخصوص برنامه‌ی خود را بسازید:

custom_exception.pyPython
class InsufficientBalanceError(Exception):
    """خطای کمبود موجودی."""
    pass


class InvalidAmountError(Exception):
    """خطای مبلغ نامعتبر."""
    pass


def withdraw(balance, amount):
    """از حساب برداشت می‌کند."""
    if amount <= 0:
        raise InvalidAmountError(f"مبلغ {amount} نامعتبر است.")
    if amount > balance:
        raise InsufficientBalanceError(
            f"موجودی {balance} برای برداشت {amount} کافی نیست."
        )
    return balance - amount


# استفاده
try:
    new_balance = withdraw(1000, 1500)
    print(f"موجودی جدید: {new_balance}")
except InvalidAmountError as e:
    print(f"⚠️ {e}")
except InsufficientBalanceError as e:
    print(f"💸 {e}")

۸) logging — به‌جای print

در فصل‌های قبل، برای دیدن آنچه در برنامه می‌گذرد از print استفاده می‌کردیم. اما در برنامه‌های واقعی، print کافی نیست. باید از logging استفاده کنید:

logging_intro.pyPython
import logging

# تنظیمات ساده
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
)

logging.debug("این پیام معمولاً نمایش داده نمی‌شود.")
logging.info("برنامه شروع شد.")
logging.warning("این یک هشدار است.")
logging.error("یک خطا رخ داد!")
logging.critical("خطای بحرانی!")

پنج سطح لاگ

هر پیام یکی از پنج سطح را دارد:

  • DEBUG — اطلاعات جزئی برای توسعه.
  • INFO — رویدادهای معمول (مثل «کاربر وارد شد»).
  • WARNING — هشدار، ولی برنامه هنوز کار می‌کند.
  • ERROR — خطا، ولی برنامه ادامه می‌دهد.
  • CRITICAL — خطای بحرانی، برنامه باید متوقف شود.

با تنظیم level=logging.INFO، همه‌ی پیام‌های INFO و بالاتر نمایش داده می‌شوند (INFO، WARNING، ERROR، CRITICAL). پیام‌های DEBUG نادیده گرفته می‌شوند.

ذخیره در فایل

logging_to_file.pyPython
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    filename="app.log",       # به فایل می‌رود، نه کنسول
)

logging.info("این پیام در فایل app.log ذخیره می‌شود.")

فایل app.log در پوشه‌ی جاری ساخته می‌شود و پیام‌ها در آن ذخیره می‌شوند.

logging در try/except

بهترین دوست try/except، logging است:

logging_in_try.pyPython
import logging

logging.basicConfig(level=logging.INFO)

def divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        logging.error(f"تلاش برای تقسیم {a} بر صفر")
        return None
    except TypeError as e:
        logging.error(f"نوع داده اشتباه: {e}")
        return None


print(divide(10, 2))
print(divide(10, 0))

۹) کِی از try/except استفاده کنیم؟ کِی نه؟

این یکی از مهم‌ترین سؤالاتی است که هر برنامه‌نویس باید بداند. بیایید با مثال:

✅ وقتی استفاده کنید:

  • ورودی کاربر: کاربر ممکن است هر چیزی وارد کند.
  • کار با فایل: فایل ممکن است نباشد یا قابل خواندن نباشد.
  • درخواست‌های شبکه: اتصال ممکن است قطع شود.
  • تقسیم: مخرج ممکن است صفر باشد.
  • تبدیل نوع: متن ممکن است قابل تبدیل نباشد.

❌ وقتی استفاده نکنید:

  • باگ‌های منطقی: اگر کد شما مشکل منطقی دارد، try/except راه‌حل نیست — باید کد را اصلاح کنید.
  • پنهان کردن خطاهای واقعی: مثلاً except Exception: pass که همه‌چیز را می‌بلعد و هیچ کاری نمی‌کند. این کار باعث می‌شود باگ‌ها پنهان شوند و بعداً پیدا کردنشان سخت‌تر شود.
  • وقتی می‌توانید از قبل بررسی کنید: گاهی بهتر است قبل از وقوع خطا، شرط را چک کنید. مثلاً به‌جای try/except برای تقسیم، از قبل چک کنید که مخرج صفر نباشد.
❌ هرگز این کار را نکنید

    do_something()

بیایید یک برنامه‌ی «ماشین‌حساب امن» بسازیم که تمام مفاهیم این فصل را کنار هم داشته باشد:

safe_calculator.pyPython
"""ماشین‌حساب امن — با مدیریت خطا و لاگ."""

import logging

# تنظیمات لاگ
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    datefmt="%H:%M:%S",
)


class CalculatorError(Exception):
    """خطای پایه‌ی ماشین‌حساب."""
    pass


def get_number(prompt):
    """یک عدد از کاربر می‌گیرد، با مدیریت خطا."""
    while True:
        try:
            text = input(prompt).strip()
            if not text:
                raise CalculatorError("ورودی خالی است.")
            return float(text)
        except ValueError:
            logging.warning(f"ورودی نامعتبر: '{text}'")
            print("⚠️ عدد معتبر وارد کن.")
        except CalculatorError as e:
            logging.warning(str(e))
            print(f"⚠️ {e}")


def get_operation():
    """عملگر را از کاربر می‌گیرد."""
    valid_ops = ["+", "-", "*", "/"]
    while True:
        op = input("عملگر (+, -, *, /): ").strip()
        if op in valid_ops:
            return op
        logging.warning(f"عملگر نامعتبر: '{op}'")
        print("⚠️ عملگر نامعتبر است.")


def calculate(a, op, b):
    """محاسبه را انجام می‌دهد، با مدیریت خطا."""
    try:
        if op == "+":
            return a + b
        if op == "-":
            return a - b
        if op == "*":
            return a * b
        if op == "/":
            if b == 0:
                raise CalculatorError("تقسیم بر صفر مجاز نیست.")
            return a / b
    except CalculatorError as e:
        logging.error(f"خطای محاسبه: {e}")
        raise


def main():
    print("=" * 40)
    print("        ماشین‌حساب امن")
    print("=" * 40)
    logging.info("برنامه شروع شد.")

    try:
        a = get_number("عدد اول: ")
        op = get_operation()
        b = get_number("عدد دوم: ")

        result = calculate(a, op, b)
        print()
        print(f"✅ {a} {op} {b} = {result}")
        logging.info(f"محاسبه موفق: {a} {op} {b} = {result}")

    except CalculatorError as e:
        print(f"\n❌ خطا: {e}")
    except Exception as e:
        print(f"\n❌ خطای غیرمنتظره: {e}")
        logging.exception("خطای غیرمنتظره رخ داد.")
    finally:
        print("\n👋 پایان برنامه.")
        logging.info("برنامه بسته شد.")


if __name__ == "__main__":
    main()

"""خواننده‌ی امن لیست — با مدیریت خطا."""


def safe_get(items, index):
    """با مدیریت خطا یک عضو لیست را برمی‌گرداند."""
    try:
        return items[index]
    except IndexError:
        return f"❌ ایندکس {index} خارج از محدوده است."
    except TypeError:
        return "❌ ایندکس باید عدد باشد."


def safe_divide(a, b):
    """تقسیم با مدیریت خطا."""
    try:
        return a / b
    except ZeroDivisionError:
        return "❌ تقسیم بر صفر"
    except TypeError:
        return "❌ نوع داده اشتباه"


def safe_convert(text, to_type):
    """تبدیل نوع با مدیریت خطا."""
    try:
        return to_type(text)
    except ValueError:
        return f"❌ نمی‌توان '{text}' را به {to_type.__name__} تبدیل کرد"
    except Exception as e:
        return f"❌ خطا: {e}"


def main():

"""ورود ایمن کاربر — با اعتبارسنجی و مدیریت خطا."""

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    datefmt="%H:%M:%S",
)


class ValidationError(Exception):
    """خطای اعتبارسنجی ورودی."""
    pass


def get_username():
    """نام کاربری معتبر از کاربر می‌گیرد."""
    username = input("نام کاربری: ").strip()

    if not username:
        raise ValidationError("نام کاربری نمی‌تواند خالی باشد.")
    if len(username) < 3:
        raise ValidationError("نام کاربری باید حداقل ۳ حرف باشد.")
    if not username.isalnum():
        raise ValidationError("نام کاربری فقط حروف و اعداد می‌پذیرد.")

    return username


def get_password():
    """رمز عبور معتبر از کاربر می‌گیرد."""
    password = input("رمز عبور: ")

    if len(password) < 6:
        raise ValidationError("رمز عبور باید حداقل ۶ حرف باشد.")
    if not any(c.isdigit() for c in password):
        raise ValidationError("رمز عبور باید حداقل یک عدد داشته باشد.")

    return password


def get_age():
    """سن معتبر از کاربر می‌گیرد."""
    text = input("سن: ").strip()

    try:
        age = int(text)
    except ValueError:
        raise ValidationError(f"سن '{text}' یک عدد معتبر نیست.")

    if not (1 <= age <= 120):
        raise ValidationError("سن باید بین ۱ و ۱۲۰ باشد.")

    return age


def main():
    print("=" * 45)
    print("       ثبت‌نام کاربر")
    print("=" * 45)

    logging.info("شروع ثبت‌نام.")

    try:
        username = get_username()
        password = get_password()
        age = get_age()

        print()
        print("-" * 45)
        print(f"✅ ثبت‌نام موفق!")
        print(f"   نام کاربری: {username}")
        print(f"   سن: {age} سال")
        print("-" * 45)

        logging.info(f"ثبت‌نام موفق: {username}")

    except ValidationError as e:
        print(f"\n❌ خطای اعتبارسنجی: {e}")
        logging.error(f"اعتبارسنجی ناموفق: {e}")
    except Exception as e:
        print(f"\n❌ خطای غیرمنتظره: {e}")
        logging.exception("خطای غیرمنتظره")
    finally:
        print("\n👋 پایان ثبت‌نام.")


if __name__ == "__main__":
    main()

🐞 خطاهای رایج و رفع آن‌ها

این خطاها را در تمرین‌ها زیاد می‌بینید:

❌ except خالی یا except Exception: pass

معنی: همه‌ی خطاها بی‌صدا نادیده گرفته می‌شوند.

علت: نوشته‌اید except: pass یا except Exception: pass.

راه‌حل: همیشه except خاص بنویسید: except ValueError:. اگر واقعاً می‌خواهید همه را بگیرید، حداقل logging.exception(...) بگذارید تا در فایل لاگ ثبت شود.

❌ ترتیب اشتباه exceptها

معنی: except عمومی قبل از خاص نوشته شده و آن را «می‌بلعد».

علت: مثلاً except Exception: ... را قبل از except ValueError: ... گذاشته‌اید.

راه‌حل: همیشه exceptهای خاص را قبل از exceptهای عمومی بنویسید. پایتون اولین except منطبق را اجرا می‌کند.

❌ خطا در بلوک finally

معنی: اگر کد داخل finally خطا بدهد، خطای اصلی از بین می‌رود.

علت: بلوک finally هم می‌تواند خطا بدهد.

راه‌حل: بلوک finally را کوچک و امن نگه دارید. اگر نیاز به عملیات پیچیده دارید، آن را در تابع جدا بنویسید و در finally فقط صدایش بزنید.

❌ استفاده از try/except به‌جای if

معنی: برای جلوگیری از خطاهای قابل پیش‌بینی از try/except استفاده می‌کنید، در حالی که می‌توانستید با if چک کنید.

علت: مثلاً برای تقسیم، از try/except استفاده می‌کنید به‌جای اینکه با if b != 0 مخرج را چک کنید.

راه‌حل: قاعده‌ی ساده: اگر می‌توانید خطا را با یک شرط ساده جلوگیری کنید، از if استفاده کنید. اگر نه، try/except.

❌ بازنویسی خطا با پیام مبهم

معنی: وقتی خطا را می‌گیرید، پیام اصلی را از دست می‌دهید.

علت: مثلاً می‌نویسید except Exception: print("خطا!") بدون اینکه پیام اصلی را نشان دهید.

راه‌حل: با as e پیام اصلی را بگیرید و نمایش دهید: except Exception as e: print(f"خطا: {e}"). یا حداقل raise کنید تا خطا به بالا برسد.

❌ فراموش کردن except برای استثنای سفارشی

معنی: خطای سفارشی پرتاب می‌شود ولی هیچ‌جا گرفته نمی‌شود.

علت: استثنای سفارشی تعریف کرده‌اید، پرتاب می‌کنید، اما except مربوطه را ننوشته‌اید.

راه‌حل: حتماً in except برای استثنای سفارشی بنویسید، یا آن را از یک استثنای بالاتر (مثل Exception) ارث‌بری کنید تا با exceptهای عمومی هم گرفته شود.

❌ logging.exception بیرون از except

معنی: پیام لاگ شامل traceback نیست.

علت: logging.exception(...) را بیرون از بلوک except صدا زده‌اید.

راه‌حل: logging.exception() باید داخل بلوک except باشد تا traceback را ثبت کند. اگر بیرون هست، از logging.error() استفاده کنید.

def safe_average(numbers):
    """میانگین امن — با مدیریت خطا."""
    try:
        # بررسی لیست خالی
        if not numbers:
            raise ValueError("لیست نمی‌تواند خالی باشد.")
        # محاسبه
        total = sum(numbers)
        return total / len(numbers)
    except TypeError:
        return "❌ همه‌ی اعضا باید عدد باشند."
    except ValueError as e:
        return f"❌ {e}"
    except Exception as e:
        return f"❌ خطای غیرمنتظره: {e}"


# تست
print(safe_average([10, 20, 30]))        # 20.0
print(safe_average([]))                  # ❌ لیست نمی‌تواند خالی باشد.
print(safe_average([10, "abc", 30]))     # ❌ همه‌ی اعضا باید عدد باشند.
print(safe_average([10, 20, None]))      # ❌ همه‌ی اعضا باید عدد باشند.

نکته: تابع به‌جای این‌که با خطا متوقف شود، پیام مناسب برمی‌گرداند. این الگو به شما اجازه می‌دهد بدون نگرانی از کرش، از تابع استفاده کنید.

یک نکته‌ی حرفه‌ای: به‌جای برگرداندن رشته، می‌توانید خطا را raise کنید و در سطح بالاتر مدیریتش کنید. هر دو رویکرد درست است — بسته به اینکه چگونه می‌خواهید برنامه ساختار داشته باشد.

🏋️ تمرین خطایابی — چهار خطا

این کد چهار خطا دارد. هر کدام را پیدا کنید:

broken.pyPython
# خطا 1 — except خیلی عمومی که خطاها را پنهان می‌کند
try:
    result = 10 / 0
except:
    pass

# خطا 2 — ترتیب اشتباه exceptها
try:
    number = int("abc")
except Exception:
    print("خطای عمومی")
except ValueError:
    print("خطای خاص")

# خطا 3 — finally فقط بعد از except می‌آید ولی بدون try استفاده شده
finally:
    print("تمیزکاری")

# خطا 4 — raise بدون استثنای مناسب بیرون از except
if True:
    raise "این یک رشته است، نه استثنا"

پاسخ:

  • خطا ۱: except: pass خطا را بی‌صدا پنهان می‌کند. راه‌حل: except ZeroDivisionError as e: print(f"خطا: {e}") یا حداقل logging کنید.
  • خطا ۲: except Exception قبل از except ValueError نوشته شده. راه‌حل: ترتیب را برعکس کنید — خاص اول، عمومی بعد.
  • خطا ۳: finally بدون try استفاده شده. راه‌حل: باید داخل یک بلوک try/except باشد.
  • خطا ۴: raise باید یک استثنا بگیرد، نه یک رشته. راه‌حل: raise ValueError("...") یا raise RuntimeError("...").

نسخه‌ی اصلاح‌شده:

fixed.pyPython
# اصلاح 1
try:
    result = 10 / 0
except ZeroDivisionError as e:
    print(f"خطا: {e}")

# اصلاح 2
try:
    number = int("abc")
except ValueError:
    print("خطای خاص")
except Exception:
    print("خطای عمومی")

# اصلاح 3
try:
    print("انجام کار")
finally:
    print("تمیزکاری")

# اصلاح 4
if True:
    raise ValueError("پیام خطا")

📝 آزمون تعاملی فصل

پرسش‌های چهارگزینه‌ای زیر را پاسخ دهید؛ بلافاصله بعد از انتخاب، پاسخ درست و توضیحش را می‌بینید. حد نصاب قبولی ۶۰٪ است و بهترین نمره‌تان ذخیره می‌شود.

۱) کدام کلیدواژه برای گرفتن خطا استفاده می‌شود؟

💡 در پایتون، خطاها را با except می‌گیریم، نه catch (که در Java و C# رایج است).

۲) خروجی این کد چیست؟
try:
    x = 10 / 0
except ZeroDivisionError:
    print("A")
finally:
    print("B")

💡 except اجرا می‌شود (چون ZeroDivisionError رخ داده) و finally هم همیشه اجرا می‌شود. پس هر دو A و B چاپ می‌شوند.

۳) برای پرتاب یک خطا از داخل تابع، از چه دستوری استفاده می‌کنیم؟

💡 در پایتون از raise استفاده می‌شود (نه throw که در Java و C++ رایج است).

۴) کدام except باید قبل از بقیه نوشته شود؟

💡 پایتون اولین except منطبق را اجرا می‌کند. اگر except Exception را اول بگذارید، همه‌ی خطاها را می‌گیرد و exceptهای خاص هرگز اجرا نمی‌شوند. پس خاص اول، عمومی بعد.

۵) finally چه زمانی اجرا می‌شود؟

💡 بلوک finally همیشه اجرا می‌شود — چه خطا رخ دهد، چه نه، حتی اگر با return از تابع خارج شوید. کاربرد اصلی‌اش پاک‌سازی منابع است.

۶) چرا except: pass کار بدی است؟

💡 except: pass هر خطایی را می‌گیرد و هیچ کاری نمی‌کند. این باعث می‌شود باگ‌های واقعی در کدتان هیچ‌وقت دیده نشوند. همیشه except خاص بنویسید و حداقل خطا را log کنید.

🏗️ پروژه عملی فصل

پروژه: «سیستم ثبت سفارش فروشگاه» — یک برنامه‌ی کامل که سفارش می‌گیرد، اعتبارسنجی می‌کند، خطاها را مدیریت می‌کند و رویدادها را ثبت می‌کند.

نیازمندی‌ها:

  • فایل در پوشه‌ی پروژه به نام online_shop.py ذخیره شود.
  • حداقل سه استثنای سفارشی تعریف شوند:
    • OutOfStockError — کالا موجود نیست.
    • InvalidQuantityError — تعداد سفارش نامعتبر.
    • PaymentError — خطای پرداخت.
  • یک «انبار» به‌صورت دیکشنری داشته باشید: {"سیب": 50, "موز": 30, "پرتقال": 20}.
  • تابع place_order(product, quantity, payment_method) که:
    • بررسی کند کالا در انبار هست.
    • بررسی کند تعداد مثبت و عدد باشد.
    • بررسی کند موجودی کافی هست.
    • پرداخت را شبیه‌سازی کند (مثلاً اگر payment_method خالی بود، خطا).
    • در صورت موفقیت، موجودی را کم کند و تأییدیه برگرداند.
  • تابع main() با یک منوی تعاملی که:
    • سفارش جدید می‌گیرد.
    • موجودی انبار را نمایش دهد.
    • هر خطا را با پیام مناسب گزارش دهد.
    • هر رویداد را با logging ثبت کند.
  • در بلوک finally همیشه یک پیام «اتصال بسته شد» یا مشابه چاپ کنید.

❓ سوالات متداول و گام بعدی

آیا می‌توانم بیش از یک except برای یک try بنویسم؟

بله، هر تعداد که لازم باشد. اما ترتیب مهم است: خاص‌ترین except را اول، عمومی‌ترین را آخر. اگر except Exception اول باشد، هیچ except دیگری اجرا نمی‌شود.

آیا finally همیشه اجرا می‌شود، حتی اگر return در try باشد؟

بله، همیشه. این یکی از ویژگی‌های مهم finally است. حتی اگر در try یک return باشد، پایتون اول finally را اجرا می‌کند و بعد از تابع خارج می‌شود. مگر اینکه در finally هم return یا exit() صدا زده شود که اصلاً کار خوبی نیست.

آیا استثنای سفارشی رو باید از Exception ارث‌بری کنه؟

بله، تقریباً همیشه. برای این که بتواند با try/except گرفته شود، باید از Exception (یا زیرکلاس‌های آن) ارث‌بری کند. در فصل ۱۶ (شی‌گرایی) این را کامل یاد می‌گیرید.

تفاوت logging.error و logging.exception چیست؟

logging.error(msg) فقط پیام شما را ثبت می‌کند. اما logging.exception(msg) علاوه بر پیام، traceback کامل خطا را هم ثبت می‌کند — یعنی دقیقاً می‌فهمید خطا در کدام خط و از کدام تابع آمده. logging.exception را باید داخل except صدا بزنید.

چطور بفهمم چه خطاهایی ممکن است رخ دهد؟

سه راه: (۱) تجربه — بعد از چند بار اجرای کد، خطاهای رایج را می‌شناسید. (۲) مستندات — در مستندات رسمی پایتون، بخش "Raises" هر تابع، لیست خطاهای ممکن است. (۳) تست — با ورودی‌های مختلف (به‌ویژه بد) کد را آزمایش کنید.
